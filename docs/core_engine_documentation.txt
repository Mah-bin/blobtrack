================================================================================
 FILE: hasher.py — SHA-256 Cryptographic Fingerprinting Engine
================================================================================

MODULE OVERVIEW:
    This module provides SHA-256 hashing capabilities:
    1. hash_bytes()            — Hash raw bytes in memory (for individual chunks)
    2. hash_file_streaming()   — Hash an entire file from disk without loading it into RAM
    3. hash_chunks_from_stream() — Hash chunks from a generator stream using a thread pool

    All hashing uses SHA-256, the same algorithm that secures Bitcoin and HTTPS.
    The probability of two different inputs producing the same hash is 1 in 2^256,
    which is larger than the number of atoms in the observable universe.

CONSTANT: STREAM_BUFFER_SIZE = 64 MB
    Size of the I/O buffer when streaming a file from disk.
    64 MB is large enough for fast I/O but small enough to never overflow RAM.

FUNCTION: hash_bytes(data: bytes) -> str
    Compute the SHA-256 hash of a raw byte sequence.
    Args:
        data: The raw bytes to fingerprint.
    Returns:
        A 64-character lowercase hexadecimal string (the SHA-256 digest).

FUNCTION: hash_file_streaming(filepath: str) -> str
    Compute the SHA-256 hash of an entire file by streaming it from disk
    in 64 MB buffers. This ensures the file is NEVER fully loaded into RAM,
    making it safe to hash files of any size (even 500 GB+).
    Args:
        filepath: Absolute or relative path to the file.
    Returns:
        A 64-character lowercase hexadecimal string.

FUNCTION: hash_chunks_from_stream(chunk_stream: Generator, max_workers=8) -> List[Tuple[int, str]]
    Hash chunks from a generator stream using a thread pool.

    CRITICAL DESIGN DECISION:
        The previous version (hash_chunks_parallel) required a fully populated
        List[Tuple[int, bytes]] as input. This forced the caller to buffer
        gigabytes of chunk data into memory before hashing could begin.

        This new version consumes a generator (from chunk_file_streaming),
        submitting hashing jobs to the thread pool as chunks arrive one-by-one
        from the stream. Each chunk is processed and discarded immediately,
        keeping memory usage flat regardless of file size.

    Args:
        chunk_stream: A generator yielding ChunkData objects (from chunker.py).
        max_workers: Maximum number of concurrent threads (default: 8).
    Returns:
        A list of (chunk_index, sha256_hex_string) tuples, sorted by index.


================================================================================
 FILE: chunker.py — Content-Defined Chunking (CDC) Engine
================================================================================

MODULE OVERVIEW:
    This is the heart of the entire project. This module takes a massive
    binary file and mathematically slices it into variable-sized chunks
    based on the actual byte patterns inside the data.

    WHY VARIABLE-SIZED (CDC) INSTEAD OF FIXED-SIZED?
        If we cut every 2 MB exactly (fixed), inserting 1 byte at the start
        of a file would shift ALL chunk boundaries, changing every single
        chunk's hash and destroying deduplication completely.

        CDC uses a Rolling Hash that scans the bytes and cuts whenever it
        detects a specific mathematical pattern. Because the cut points are
        determined by the DATA ITSELF (not by position), inserting bytes only
        affects the chunks immediately around the insertion point. All other
        chunks remain identical, preserving deduplication.

    CHUNK SIZE CONSTRAINTS:
        - Minimum: 512 KB  (prevents creating millions of tiny chunks)
        - Average: 2 MB    (the target size for most chunks)
        - Maximum: 8 MB    (prevents a single chunk from getting too large)

    ARCHITECTURE (v2 — MEMORY-SAFE):
        The original chunk_file() function loaded all chunk data bytes into
        an in-memory list. A 20GB file would instantly crash the tool (OOM).

        The redesigned architecture separates metadata from data:
        - ChunkMeta: Lightweight object (index, offset, length, hash). Safe to
          collect thousands of these in a list — uses negligible RAM.
        - ChunkData: Heavy object (meta + raw bytes). Only exists momentarily
          inside the streaming generator, then is garbage-collected.

        The original _read_chunk_data() helper opened and closed the file for
        every single chunk, causing disk thrashing on thousands of chunks.
        The new design keeps a single file handle open for the entire chunking
        operation using a `with open()` context manager.

CONSTANTS:
    MIN_CHUNK_SIZE = 512 * 1024        (512 KB)
    AVG_CHUNK_SIZE = 2 * 1024 * 1024   (2 MB)
    MAX_CHUNK_SIZE = 8 * 1024 * 1024   (8 MB)

CLASS: ChunkMeta
    Lightweight metadata for a single chunk. Does NOT hold raw data bytes.
    Safe to collect thousands of these in a list without memory issues.
    Attributes:
        index:      The chunk's position in the file (0-based).
        offset:     The byte offset where this chunk starts in the original file.
        length:     The length of this chunk in bytes.
        hash:       The SHA-256 fingerprint of this chunk's raw data.

CLASS: ChunkData
    Heavy object containing both metadata and raw bytes.
    Should only exist momentarily inside a streaming generator.
    Attributes:
        meta:       A ChunkMeta object.
        data:       The raw (uncompressed) bytes of this chunk.

FUNCTION: chunk_file_streaming(filepath: str) -> Generator[ChunkData, None, None]
    The primary chunking function. Yields one ChunkData at a time.
    Only one chunk's worth of raw bytes exists in RAM at any given moment.
    The file handle is kept open for the entire operation (single open/close).
    Args:
        filepath: Path to the file to chunk.
    Yields:
        ChunkData objects, one at a time, in file order.
    Raises:
        FileNotFoundError: If the file does not exist.
        ValueError: If the file is empty.

FUNCTION: chunk_file_metadata_only(filepath: str) -> List[ChunkMeta]
    Chunks the file but only returns lightweight metadata (no raw bytes stored).
    Safe to call on files of any size because ChunkMeta objects are tiny.
    Used when you need the list of chunk hashes (e.g., for building a Merkle Tree)
    without holding the actual data in memory.
    Args:
        filepath: Path to the file to chunk.
    Returns:
        An ordered list of ChunkMeta objects.

FUNCTION: read_chunk_at(filepath, offset, length) -> bytes
    Read a specific byte range from a file on disk.
    Uses seek() to jump directly to the chunk's starting position.
    Used during file reconstruction to fetch individual chunks on demand.
    Args:
        filepath: Path to the file.
        offset:   Byte position to start reading from.
        length:   Number of bytes to read.
    Returns:
        The raw bytes for this chunk.

FUNCTION: get_file_info(filepath: str) -> dict
    Get basic file information before chunking.
    Returns:
        A dictionary containing filename, size in bytes, and human-readable size.


================================================================================
 FILE: packer.py — Zstandard Compression / Decompression Engine
================================================================================

MODULE OVERVIEW:
    This module compresses chunk data before storing it on disk, and
    decompresses it when reading chunks back for file reconstruction.

    We use Zstandard (Zstd) because:
    - Compression speed: ~500 MB/s (fast enough to not bottleneck the pipeline)
    - Decompression speed: ~4-5 GB/s (faster than most SSDs can read)
    - Compression ratio: typically 2x-5x for binary data

    This means a 4 MB chunk might shrink to 1-2 MB on disk, further
    reducing storage requirements on top of the deduplication savings.

    NOTE: Compression is NOT called during chunking. It is called by the
    Storage Layer (local_store.py) when saving chunks to disk. This keeps
    the chunker focused solely on slicing and hashing.

CONSTANT: DEFAULT_COMPRESSION_LEVEL = 3
    Level 1 = fastest but least compression.
    Level 22 = slowest but maximum compression.
    Level 3 = excellent balance of speed and compression ratio.

FUNCTION: compress(data: bytes, level: int = 3) -> bytes
    Compress raw bytes using Zstandard.
    Args:
        data: The raw bytes to compress (e.g., a single chunk's content).
        level: Compression level (1-22). Default is 3.
    Returns:
        The compressed bytes.

FUNCTION: decompress(data: bytes) -> bytes
    Decompress Zstandard-compressed bytes back to the original raw data.
    Args:
        data: The compressed bytes to decompress.
    Returns:
        The original raw bytes.


================================================================================
 FILE: merkle_tree.py — Merkle Tree Construction & Serialization
================================================================================

MODULE OVERVIEW:
    A Merkle Tree lets us represent the entire fingerprint-state of a file
    as a single root hash. If two files (or two versions of the same file)
    produce the same root hash, they are guaranteed to be identical at the
    chunk level. If the root hashes differ, walking down the tree lets us
    prune away any subtree whose hash matches on both sides, so we only
    pay attention to the parts of the file that actually changed.

    The tree is built bottom-up from the ordered list of chunk hashes
    produced by the chunking and hashing pipeline (Member 2).

CLASS: MerkleNode
    A single node in the Merkle Tree.

    Uses __slots__ for memory efficiency — reduces per-node memory footprint,
    which matters for deep trees built from files with thousands of chunks.

    Attributes:
        hash:       The SHA-256 fingerprint of this node.
                    For leaf nodes: the chunk's hash directly from the hasher.
                    For internal nodes: SHA-256 of left.hash + right.hash concatenated.
        left:       Left child MerkleNode (None for leaf nodes).
        right:      Right child MerkleNode (None for leaf nodes).
        is_leaf:    True if this node represents a chunk (bottom of tree).
                    False if this is an internal node.

    Equality:
        Two MerkleNodes are equal if their hash and is_leaf attributes match.

FUNCTION: _combine_hashes(left_hash: str, right_hash: str) -> str  [PRIVATE]
    Hashes two child hashes together to produce their parent's hash.
    Concatenates the two hex strings, encodes to UTF-8, and runs SHA-256.
    This is the standard cryptographic method for building internal Merkle nodes.

FUNCTION: build_tree(chunk_hashes: List[str]) -> Optional[MerkleNode]
    Builds a Merkle Tree bottom-up from an ordered list of chunk fingerprints.

    Args:
        chunk_hashes: SHA-256 hex digests, one per chunk, in file order.
    Returns:
        The root MerkleNode, or None if chunk_hashes is empty.

    Odd-Number Handling:
        If a level has an odd number of nodes, the leftover node is carried
        up untouched to the next level (PROMOTED, not duplicated). Duplicating
        the node would make its chunk hash appear twice in collect_leaf_hashes(),
        silently corrupting the chunk list. Promotion keeps every chunk hash
        represented exactly once no matter how the tree balances.

    Special Cases:
        - Empty list returns None.
        - Single chunk returns that chunk as a leaf node (it is its own root).

    Algorithm:
        1. Create leaf nodes from chunk hashes (Level 0).
        2. While more than 1 node remains:
           a. Pair adjacent nodes left-to-right.
           b. Combine each pair's hashes to create a parent node.
           c. If a node has no partner (odd one out), promote it as-is.
        3. Return the final remaining node as root.

FUNCTION: serialize_tree(root: Optional[MerkleNode]) -> str
    Serializes a Merkle Tree to a JSON string for storage on disk.
    Recursively converts each node to a dictionary with keys:
    "hash", "is_leaf", "left", "right".
    Args:
        root: The root MerkleNode to serialize.
    Returns:
        A JSON string representation of the entire tree.

FUNCTION: deserialize_tree(data: str) -> Optional[MerkleNode]
    Reconstructs a Merkle Tree from a JSON string produced by serialize_tree().
    Recursively rebuilds MerkleNode objects from the dictionary structure.
    Args:
        data: A JSON string from serialize_tree().
    Returns:
        The root MerkleNode, or None if the JSON represents a null tree.

FUNCTION: collect_leaf_hashes(root: Optional[MerkleNode]) -> List[str]
    Returns every leaf (chunk) hash under this node, left-to-right in order.
    This is the "recipe" — the ordered list of chunk hashes needed to
    reconstruct the original file.
    Args:
        root: The root MerkleNode to collect from.
    Returns:
        Ordered list of chunk hash strings. Empty list if root is None.


================================================================================
 FILE: differ.py — Delta Diffing Between Two Merkle Trees
================================================================================

MODULE OVERVIEW:
    Given the Merkle Tree of a file's previous commit and the tree of its
    current state, these functions tell the rest of the system exactly which
    chunks are new, which are gone, and which are unchanged — so the storage
    and remote sync layers only have to push/pull the handful of chunks that
    actually changed.

    Two diffing strategies are provided:
    1. compute_delta()        — Positional (structural) tree walk. Fast.
    2. compute_delta_by_set() — Content-based set comparison. Accurate.

FUNCTION: compute_delta(old_tree, new_tree) -> Dict[str, List[str]]
    Top-down structural diff between two Merkle Trees.

    Walks both trees in lockstep, position by position. Whenever the hash
    at the current position matches on both sides, the whole subtree is
    pruned (a matching hash proves every chunk underneath is identical).
    This is what makes diffing a 20GB file fast: we only ever look at the
    branches that actually changed.

    Args:
        old_tree: Root MerkleNode of the previous version (or None).
        new_tree: Root MerkleNode of the current version (or None).
    Returns:
        {"added": [...], "removed": [...], "unchanged": [...]}
        Each list holds chunk hashes (hex digests).

    Algorithm (_walk recursive function):
        - Both None: return (nothing to compare).
        - Old is None: all chunks under new_tree are "added".
        - New is None: all chunks under old_tree are "removed".
        - Hashes match: entire subtree is "unchanged" (prune — don't recurse).
        - Hashes differ and either is a leaf: old chunk is "removed", new is "added".
        - Hashes differ, both internal: recurse into left and right children.

    Caveat:
        This positional walk assumes the two trees have roughly the same
        shape, which holds for most in-place edits. If chunks are inserted
        or removed in a way that shifts everything after them, a positional
        comparison can under-count how much content is actually shared.
        For that scenario, use compute_delta_by_set() instead.

FUNCTION: compute_delta_by_set(old_tree, new_tree) -> Dict[str, List[str]]
    Content-based (position-independent) diff between two Merkle Trees.

    Collects the full set of leaf hashes on each side and compares them
    with set arithmetic instead of walking the trees in lockstep.

    This is the version that should drive push()/pull() in remote_sync.py:
    content-defined chunking means a chunk can shift position in the tree
    (e.g., something was inserted earlier in the file) without its own
    content changing at all. A positional walk would wrongly flag every
    chunk after the insertion point as "changed"; set comparison correctly
    recognizes them as already-stored content that never needs re-uploading.

    Args:
        old_tree: Root MerkleNode of the previous version (or None).
        new_tree: Root MerkleNode of the current version (or None).
    Returns:
        {"added": [...], "removed": [...], "unchanged": [...]}
        Lists are sorted for deterministic output.

    Set Operations:
        - added    = new_hashes - old_hashes  (chunks only in the new version)
        - removed  = old_hashes - new_hashes  (chunks only in the old version)
        - unchanged = old_hashes & new_hashes (chunks present in both versions)
